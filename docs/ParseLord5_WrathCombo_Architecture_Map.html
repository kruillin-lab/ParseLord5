PvE Job Flow

PvE job implementations live under WrathCombo/Combos/PvE/<JOB>/. Job classes define nested CustomCombo implementations. Config files draw per-preset controls.

Warrior example WAR_ST_Simple WAR_AoE_Simple WAR_ST_Advanced WAR_AoE_Advanced

Each checks pressed base action, then uses helper logic for mits, OGCDs, GCDs, and fallback combo action.

ParseLord5 rule Tune one job at a time. Add experiments inside selected job Invoke paths only after default-false flag exists.

Safest ParseLord5 Experimental Flag

Recommended first flag: add ParseLord5ExperimentalMode to Configuration, default false, with existing Setting attributes so Settings UI picks it up by reflection. 
[SettingCategory(Main_UI_Options)]
[Setting(Setting.Type.Toggle)]
public bool ParseLord5ExperimentalMode = false;

First use should be inside one selected job's future experiment path, not in global hook or auto-rotation execution code.

Good first guard

if (Service.Configuration.ParseLord5ExperimentalMode)
{
    // ParseLord5-only experiment for one selected preset.
}

Avoid first-pass guards in

  • ActionReplacer.GetAdjustedActionDetour
  • ActionReplacer.GetAdjustedAction
  • AutoRotationController.Run
  • AutoRotationHelper.ExecuteST / ExecuteAoE
  • ActionManager.UseAction call sites
  • Command dispatch

Risk Register

  • /wrath can conflict if regular WrathCombo and ParseLord5 load together.
  • Namespaces still say WrathCombo; safe for now, noisy in logs and traces.
  • Auto-rotation uses live UseAction; tracing must not change queue, target, or range behavior.
  • ActionChanging controls hook enablement; broad changes can break all replacement behavior.
  • IPC prefix is still WrathCombo; changing it needs separate compatibility plan.
